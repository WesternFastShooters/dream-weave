A code wiki for this local repository. Prioritize a concise quickstart, architecture overview, source map, key workflows, domain concepts, operations/runbook notes, testing guidance, integration points, a canvas-node catalog, and a backend-capability map. Inspect git history to understand reasoning behind code changes and the progression of the repository. Keep pages grounded in the repository structure and recent code changes. Prefer practical navigation for engineers over generic summaries.

The wiki is a retrieval aid for coding agents, not a product overview. On every update, compare commits since the last documented Git head and make a documentation change when a commit adds or changes any of these: a persisted canvas node kind; node rendering, creation, editing, sizing, toolbar, selection, drag, lasso, zoom, or keyboard behavior; public API/protobuf; Go service ownership; persistence/migration; asset delivery; preview worker; Office/PDF session, origin, JWT, or proxy; deployment security boundary; or the applicable test path.

Maintain `domain/canvas-node-catalog.md` as the complete inventory of every `CanvasItemKind`. For each kind, record its user role/data, core model, registered renderer, creation path, server or asset dependency, and primary tests. Maintain `architecture/backend-map.md` as the map from each public/backend capability to its protobuf contract, transport, service, persistence or async work, security boundary, and tests. Link both pages from the root index, quickstart, source map, architecture/domain indexes, and relevant workflow/testing pages.

Do not treat a successful OpenWiki run with no textual diff as valid when the changed commits alter any required catalog/map entry. In that situation, update the relevant pages explicitly and include the concrete source paths; generic statements such as “creative nodes” or “server handles assets” are insufficient.
